Des factures lues
automatiquement,
sans jamais deviner

Un pipeline qui transforme les factures fournisseurs PDF de GARNIER Industrie en données vérifiées : chaque valeur incertaine est signalée, chaque écart de calcul est chiffré, et la décision reste au comptable.

Ce document présente l'architecture du pipeline et de son interface : les diagrammes de séquence, le schéma de données exact, le rôle de chaque fichier, puis la raison de chaque choix technique, les limites connues et ce qu'il faudrait pour passer à 4 000 factures par mois.

Vue d'ensemble

Deux programmes indépendants reliés par un seul fichier, results.json, et par un seul contrat de données, schema.ts.

Pipeline (Node.js)Interface (navigateur)Service externeContrat partagé

Figure 1 · Le pipeline lit les PDF, interroge Mistral, puis écrit un fichier ; l'interface lit ce fichier. La clé API ne sort jamais du pipeline.

Pipeline

  • index.ts orchestre le dossier, processInvoice.ts traite un fichier.
  • mistral.ts est le seul module qui connaît l'API.
  • normalize.ts et checks.ts sont des fonctions pures, testées sans réseau.

Interface

  • Une page React (Vite), sans serveur ni base de données.
  • Revalide results.json avec le même schéma Zod.
  • Un composant par élément visible, aucun any.

Défini une seule fois dans pipeline/src/schema.ts. Les types TypeScript en sont déduits avec z.infer. En orange, les champs qui peuvent valoir null.

DécisionPourquoi
Tout est nullableLe LLM a le droit de dire « je ne sais pas ». Un champ obligatoire le forcerait à inventer ; un 0 par défaut serait pire, car 0 € est un vrai montant.
Avertissement lié à un champL'interface l'affiche sous le bon champ (field: "totalTTC", "lineItems[2]").
Union succès / échecImpossible d'avoir à la fois des données et une erreur ; TypeScript interdit data sur un échec.

Types déduits (z.infer)Une seule description ; des interfaces écrites à la main finiraient par diverger du schéma.

7

Pourquoi ces choix

Chaque décision, et pourquoi l'alternative évidente n'a pas été retenue.

ChoixPourquoi, et pourquoi pas l'alternative
OCR puis LLM, deux appelsL'OCR lit l'image : seule façon de lire le scan et la facture mal encodée. Séparer les étapes dit si une erreur vient de la lecture ou de la compréhension.
JSON Schema strict, généré par ZodLe format est imposé par l'API au lieu d'être demandé en texte, et il n'existe qu'une description (z.toJSONSchema).
Revalidation Zod malgré le mode strictLe mode strict est une promesse du fournisseur, pas une garantie dans notre code. Une ligne attrape une réponse coupée ou un changement de modèle.
temperature: 0On extrait, on ne rédige pas : même facture, même résultat.
Contrôles par le code, pas par le LLMUn LLM peut affirmer un calcul faux ; le code calcule juste, gratuitement, toujours pareil.
Centimes entiers, tolérance 1 centimeEn JavaScript, 0,1 + 0,2 ≠ 0,3 ; les entiers sont exacts. Un centime couvre les arrondis imprimés.
Trois statuts de contrôleSi une valeur manque, ni « juste » ni « faux » n'est vrai : « non vérifiable » évite le faux écart comme la fausse assurance.
Total de ligne impriméRecalculer fabriquerait une facture juste et cacherait l'erreur du fournisseur.
Mistral isolé dans un fichierChanger de fournisseur ou simuler l'API dans les tests ne touche qu'un fichier.
Client créé au premier appelLes import s'exécutent avant main(), donc avant le .env : créé à l'import, le client ne verrait pas la clé.
Délai 60 s, relances croissantesPar défaut, le SDK attend 5 minutes et ne relance jamais. Attendre de plus en plus évite d'aggraver une surcharge.
Concurrence limitée (2)Une boucle est lente ; Promise.all sur tout le dossier provoque des 429. Un nombre fixe concilie les deux.
Signature %PDF- vérifiéeUn faux PDF donne un message clair et ne consomme pas de requête.
Fichier JSON, pas de serveurLe sujet demande une page sans base ni authentification. Rien à héberger, la clé reste côté pipeline.
React + Vite, TypeScript strictSuffisant pour une page, sans sur-construction. strict et noUncheckedIndexedAccess forcent à traiter chaque null.

Erreurs, interface, tests, Docker

Gestion des erreurs

CasComportement
Clé absente, dossier introuvable ou videArrêt immédiat, message avec la solution
Fichier illisible ou pas un PDFÉchec pour ce fichier, sans appel à l'API
OCR vide, réponse non JSON ou hors schémaÉchec pour ce fichier, avec le détail Zod
429, 5xx, réseau, délai dépasséRelances automatiques, puis échec lisible
401 et autres erreurs HTTPÉchec sans relance, message explicite

Interface

  • Lisibilité : résumé par statut en haut, une carte par PDF.
  • Incertitude visible : écarts et avertissements en tête de carte, « Non lu » en orange, ligne en écart surlignée en rouge, symboles ✓ ✗ ? en plus des couleurs.
  • Traçabilité : le nom du fichier titre chaque carte.
  • Robustesse : results.json d'un ancien format → message clair.

Tests (65, npm test)

  • Schéma : montant en texte refusé, absent ≠ null.
  • Contrôles : cas Studio Botanica, 0,1 + 0,2, valeurs manquantes.
  • Dates impossibles, quantité « 0 », avertissements sans doublon.
  • Erreurs Mistral traduites ; API simulée : faux PDF, hors schéma, 429.
  • Concurrence : ordre gardé, limite respectée.

Docker

Une image node:22-slim installe les dépendances (couche mise en cache), lance le pipeline puis sert l'interface : docker compose up --build, puis http://localhost:5173. La clé est lue au démarrage depuis .env (env_file) et n'est jamais copiée dans l'image (.dockerignore). Les factures sont montées en lecture seule.

Pourquoi ne pas tout résoudre par le prompt ? Le prompt demande déjà de ne jamais inventer, et le LLM a tout de même recopié « 0 ». Une consigne réduit le risque, seul le code le garantit : c'est le même principe que la revalidation Zod après le mode strict.

Limites connues et passage à 4 000 factures

Limites

  • Une valeur cachée sur le document (tache, rature) peut être inventée par l'OCR ; seuls la quantité « 0 » et les écarts de calcul sont rattrapés (section 10).
  • Une valeur plausible mais mal lue ou mal attribuée peut passer tous les contrôles : échéance prise pour la date d'émission, référence de commande prise pour le numéro, jour et mois inversés. La relecture humaine reste nécessaire.
  • Provenance au niveau du fichier, pas de la page ni de la position dans le PDF.
  • Euro uniquement ; pas d'avoirs, de remises ni de TVA par ligne.
  • Le nom du client (GARNIER Industrie) est écrit dans le prompt ; pour plusieurs clients, il deviendrait une configuration.
  • Les factures partent vers une API externe (Mistral, hébergé dans l'UE) : à valider avec le client pour des données réelles.

De 4 à 4 000 factures par mois

Traitement

  • File d'attente + workers (BullMQ/Redis ou SQS) : chaque facture est un travail indépendant, relancé seul.
  • Débit : concurrence réglée sur le quota Mistral.
  • Cache par empreinte SHA-256 : un doublon n'est jamais retraité.

Données et qualité

  • PostgreSQL pour résultats, statuts et historique ; une petite API pour l'interface.
  • Corrections enregistrées (qui, quoi, quand), réutilisées comme jeu de test à chaque changement de prompt ou de modèle.
  • Contrôles enrichis : fournisseur par SIRET, détection des doublons ; suivi du coût et du taux d'échec.
